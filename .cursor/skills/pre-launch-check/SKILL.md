# 公開前確認

本番公開前の **最終確認手順書**。確認項目をフェーズごとに会話で進める。各 Step は **スキップ** 可。

実装直後のセルフチェック（`@figma-page-implement` Phase 3／`@figma-coding` Step 4。コンソール＋大差の報告。ページ 1 件の vnu と規約は `page-check.md`）とは **別物**。本スキルの M-6 と vnu はサイト全体。微差を含む見た目確認は、公開前の人間向け確認促しが主目的。

OGP・Favicon・テーマカラー・WP 管理画面は **本スキル（M-1 / M-2）で確認し、必要ならセットアップ**する（旧 `@project-env-setup` D）。手順は [reference.md](reference.md)「仕上げセットアップ」。UI 系カラー（選択・フォーカス・スクロールバー等）は **M-1-5 で確認のみ**（対応は手動。エージェントは編集しない）。`@project-env-setup` は環境・pages・スタイル基盤まで（UI 色の初期設定は C-1）。

**本スキルの意図外**（対象にしない）:

- お問い合わせメールの宛先・SMTP 設定の棚卸し（お客様含む動作確認で担保。実送信は M-8）
- 管理 URL・ユーザーアカウントの棚卸し（運用／納品側。W-3 は廃止）

## 進め方（AskQuestion 優先）

ユーザー確認は **`AskQuestion`（選択式）** で行う。共通パターンは [project-page-info/SKILL.md](../project-page-info/SKILL.md) の「進め方（AskQuestion 優先）」に準拠。

| ルール | 内容 |
|--------|------|
| 1 Step ずつ | 次へ進むのは現 Step の回答（確認済み・スキップ等）後 |
| AskQuestion 必須 | 末尾に **「その他（続けてチャットで指定）」** を置く |
| 情報提示 | 現状値・確認観点は AskQuestion の **直前** にチャットで提示 |
| 編集ポリシー | **M-8 は原則編集しない**（読む・促すのみ）。**M-1-5 は確認のみ**（要対応時は手動作業を促す。エージェントは変数・スタイルを編集しない）。**M-1（M-1-5 除く）/ M-2 は確認に加え、ユーザー承認後のセットアップ編集可**（OGP 配置案内・`THEME_COLOR`・管理画面色・**PHP の `make sitemap` / `make htaccess`** など）。**M-3（不要コード削除）・M-4（TODO 追記）・M-5（誤字脱字の修正）・M-6（規約違反の修正。実施を選んだとき）・HTML 構文（vnu。実施を選んだとき。一括チェックはエージェントが実行し、マークアップ修正は承認後）・M-7（フォーム不備の修正）は承認後に編集可** |
| 機密 | パスワード・SMTP・API キー等をチャットに載せない |

スキップした Step は一覧に残し、**M-4-3 で TODO 化**する。

再実行時は未完了 Step から再開する。

## M-1: meta 系確認（M-1-5 除き承認後はセットアップ編集可）

配置・セットアップ: [reference.md](reference.md)「M-1」「仕上げセットアップ（旧 project-env-setup D）」。**M-1-5（UI 系カラー）は確認のみ。**

### M-1-1: 基本 meta

1. 現状値を読み取り提示（title/description、OGP、Favicon、`THEME_COLOR`、`SITE_NAME`、`site.webmanifest` の `name` / `short_name`）。
2. **仮設定・サンプル残りを併せて洗い出し報告する**（[reference.md](reference.md)「M-1-1」の仮設定例）。ヒットが無くても「仮設定候補なし」と明示する。
3. **`AskQuestion`**: 問題なし / 修正が必要 / スキップ

### M-1-2: noindex

1. `pages.php`（CPT は `posts.php`）の `noindex` を一覧化。本番公開すべき画面に `true` が残っていないか、確認画面等に適切か。
2. 出力経路（PHP: `includes/meta/noindex.php` 等）の存在を確認。
3. **`AskQuestion`**: 問題なし / 修正が必要 / スキップ

### M-1-3: 構造化データ

1. 案件内の構造化データ実装を探す（JSON-LD、Microdata、パンくずの `schema.org` 等）。参考: [reference.md](reference.md)「M-1-3」。
2. 必須要件が依頼・仕様にあれば突合。無ければ「現状の実装有無」を提示。
3. **`AskQuestion`**: 問題なし / 要追加・修正 / 対象外・スキップ

### M-1-4: 計測タグ（GTM / GA 等）

1. PHP: `includes/config/tracking-tags.php` の `GTM_CONTAINER_ID` / `GA4_MEASUREMENT_ID` 等と、`tracking-tags.php` / `tracking-tags-body.php` の読み込みを確認。
2. WordPress: テーマまたはプラグイン側の同等設定を探し現状を提示。
3. 本番 ID が入っているか、空のままか、ローカル用のままかを明示（値の全文は必要最小限。秘密情報は載せない）。
4. **`AskQuestion`**: 本番向け設定済み / 未設定・要対応 / 対象外・スキップ

「修正が必要」の場合（**M-1-1〜M-1-4**）は項目を整理し、**本フェーズでセットアップ対応してよいか AskQuestion**する。承認後に編集／手動配置を案内する（[reference.md](reference.md)「仕上げセットアップ」）。

### M-1-5: UI 系カラー（確認のみ・手動対応）

選択色・フォーカス色・スクロールバー色など、`$colors` の `ui/*` および UI フラット変数。初期設定は `@project-env-setup` C-1（`@figma-tokens-setup`）。**本 Step は確認と手動対応の促しのみ。エージェントは `_variables.scss` 等を編集しない。**

詳細観点・変数一覧: [reference.md](reference.md)「M-1-5」。正本の色ルールは `project/css/scss.mdc`「UI フラット変数」。

1. `_variables.scss` の現状を読み取り、表で提示する（コメントアウト／有効、`$colors` の `ui/*` 有無、テンプレ／サンプル色の残り）。
2. 確認観点を短く示す（選択・フォーカス・スクロールバーが案件色か、未設定のままでよいか、ブラウザでの見た目確認は M-8 でも可）。
3. 要対応時の手動手順を案内するのみ（コメント解除・`ui/*` の値更新、または `@figma-tokens-setup` / `@figma-tokens-sync`）。コード変更はユーザー側。
4. **`AskQuestion`**: 問題なし（現状で公開可） / 要対応（手動で直す・本 Step では編集しない） / スキップ

「要対応」なら Open として完了報告・**M-4-3 の TODO 化候補**に残す。エージェントが代行編集しない旨を明示する。

### M-1-6: サイトマップ確認・生成（PHP は htaccess も同時）

詳細: [reference.md](reference.md)「M-1-6」。

#### WordPress

コアの `/wp-sitemap.xml` を利用する前提。テーマは `inc/setup/sitemap-noindex.php` で `pages.php` / `posts.php` の `noindex` と整合するだけ。

1. 「**WP コア標準のサイトマップを使用。追加の独自生成は不要**」と報告する。
2. 任意で軽く: `sitemap-noindex.php` が読み込まれていること、`noindex` 方針と矛盾しそうな CPT／固定ページが無いか（深掘り不要）。
3. **`AskQuestion`**: 問題なし（標準でよい） / 要確認あり / スキップ

生成コマンドや静的 XML の作成は **WP では行わない**。

#### PHP（サイトマップ + htaccess）

公開 URL 一覧の妥当性と、**静的 `sitemap.xml` の生成**、あわせて **`000-default.conf` → `.htaccess` の突合・再生成**を同一 Step で行う。

**A. サイトマップ（内容）**

1. 次を読む: `Page::getIndexableStaticSitemapPaths()`（`pages.php`）、`includes/sitemap/entries.php`（`sitemap_additional_paths()`）、生成スクリプト `resources/scripts/write-sitemap.php`。
2. 表で提示: 載る想定／載らない想定（noindex・確認／サンクス等）／動的 URL（entries・Store）の過不足・サンプル残り。
3. ランタイム `sitemap.php` や `/sitemap.xml → sitemap.php` リライトが残っていれば要削除と報告（現行方針は静的ファイル配信）。

**B. htaccess（生成元 `000-default.conf` とサイト状態）**

生成元は `docker/php/000-default.conf`（`make htaccess` → `resources/scripts/write-htaccess.php` → `htdocs/.htaccess`）。**生成結果だけ見ず、conf の Rewrite が案件のルート構成と一致しているか**を確認する。

1. `000-default.conf` の Directory 内 Rewrite／ErrorDocument を読む。
2. サイト状態と突合する（[reference.md](reference.md)「M-1-6」の htaccess 表）:
   - 動的詳細（`/works/{id}`・`/news/{id}` 等）: `pages.php` に詳細 URL があり実ファイル（`*-detail.php`）があるのに conf の `RewriteRule` がコメントのまま／逆に不要ルールが有効、など
   - 直アクセス拒否ディレクトリ（`includes|data|src|modules` 等）が現状の公開構成と合うか
   - 旧 `sitemap.php` リライトが残っていないか（静的 `sitemap.xml` 方針）
   - `SITE_BASE_PATH`（`config.php`）と、再生成後の `.htaccess`（`RewriteBase` 等）の前提が一致するか
3. 差分・要コメント解除／要コメントアウトを表で提示する。

**C. 生成（承認後）**

1. 内容確認のあと **`AskQuestion`**: 問題なし（生成まで進める） / conf・entries 等を先に直す / スキップ
2. 「生成まで進める」なら、本番向け origin を確認したうえで:
   - `make sitemap SITEMAP_ORIGIN=https://（本番ホスト）`（ローカル確認のみなら未指定可）
   - 必要なら conf 修正後に `make htaccess`
   - 実行はユーザーが基本。AskQuestion でエージェント実行を選んだ場合のみ代行
3. conf／entries／pages の修正が先なら、修正案を示し **編集承認の AskQuestion** → 承認後に編集 → 再突合 → 生成へ

## M-2: プロジェクト固有（WordPress・承認後はセットアップ編集可）

非 WordPress の場合は本節の W-* を実施せず、「WP 固有は対象外」と完了報告に書く。

旧 **「ログイン URL 変更」** および **W-3（管理 URL・ユーザーアカウント）** は実施しない。

詳細観点は [reference.md](reference.md)「M-2 WordPress」。

| Step | 内容 |
|------|------|
| W-1 | 管理画面スタイルの最終確認 |
| W-2 | 不要な投稿・サンプルデータの棚卸し（削除はユーザー実行。下記） |
| W-4 | プラグイン操作の開発モード解除確認 |

| W-6 | 編集ガイドの確認（納品・運用向け。ブロック／ACF／投稿の編集手順など） |

各 Step は確認観点提示 → **`AskQuestion`**（確認済み / 要対応 / スキップ）。W-6 は対象外（編集ガイド不要の案件）も可。

### W-2: 不要な投稿・サンプルデータ（方法）

**エージェントは DB 上の投稿を削除しない。** 候補の棚卸しと削除手段の案内に留める。

1. 候補を表で提示する（[reference.md](reference.md)「W-2」）:
   - Hello world・テスト下書き・明らかに開発用のタイトル
   - `data/{post_type}/posts.dev.json` 由来と分かる開発用投稿が本番向け DB に残っていないか（件数・タイトルの目安）
   - 未使用メディアの目立つ残り（分かる範囲）
2. `data/` 配下の **ファイル**としてのサンプル残りは **M-3-2**（ここでは DB／管理画面側）。
3. 削除手段を案内: 管理画面、またはプロジェクトに `make wp-remove-posts` 等があればその案内（**実行はユーザー**。明示依頼時のみ代行検討）。
4. **`AskQuestion`**: 候補を把握した（削除は自分で行う） / 要対応の整理が必要 / スキップ

## M-3: 不要なコード確認（承認後に削除可）

**mixin / function の未使用検出は対象外**（今は対応しない）。

### 共通ルール（削除時・必須）

- 先に **候補一覧と根拠** を提示し、削除は **ユーザー承認後のみ**
- 次は **削除候補にしない／特に慎重**: エントリ SCSS/JS、`foundation/`、共有 `modules` で他ページ参照あり、`_template.*`、設定・ルーティングの要、ビルド設定が参照するもの
- 参照解析: Grep / `@use` / `import` / PHP `include`・class 名の使用箇所。**確信が持てないものは削除せず要確認リストへ**
- 画像・設定・`.env` は本フェーズの対象外（`data/` のサンプル JSON 等は下記 M-3-2。未使用 JS は M-3-3）
- 削除前に影響範囲を短く説明。ユーザーが拒否した候補は残す

### M-3-1: 空の SCSS セレクタ

1. `src/scss/` を調査し、中身が実質空のルール（`{}` のみ、コメントのみ等）を列挙。
2. テンプレ直後の意図的な空骨組みか、放置かを区別して注記。
3. **`AskQuestion`**: 提示した空セレクタを削除してよいか（全削除承認 / 個別はチャット / スキップ）
4. 承認分のみ削除する。

### M-3-2: 未使用部品・サンプルファイル

対象例（SCSS / テンプレート / **data/**。**JS ファイル本体は M-3-3**）:

- どこからも参照されない `modules` / `pages` の **PHP・SCSS** 部品
- 名前に `sample` / `demo` / `_template` コピー残りなど、本番不要と分かるファイル（`_template.js` 自体の雛形は消さない → M-3-3）
- 未使用の page エントリに紐づく **SCSS**（`assets_name` やルーティングと突合。JS 側は M-3-3）
- **`src/scss/_sample/`**（PHP 環境）: blocks / elements 等の参照用サンプル。コンパイル対象外だが、本番公開前に **ディレクトリごと削除候補として必ず確認**する（案件で流用・本番採用しているファイルがあれば除外）
- **`src/scss/pages/_sample/`**: サンプルページ用エントリが残っていれば同様に削除候補として確認
- **`src/scss/wp-block-editor/`** および **`src/scss/wp-block-styles.scss`**: ブロックエディタ用スタイル。案件でブロックエディタ／エディタ用 CSS を使わない・サンプルのまま残っている場合は **削除候補として必ず確認**する（`build-config` の `EXCLUDE_ENTRIES` で未使用のまま除外されていることも多い）。本番で使うカスタムブロックスタイルがある場合は残す／一部のみ削除
- **`data/` 配下**: 開発用サンプル（例: `posts.dev.json`、`*.sample.json`、使っていない media／contact サンプル）の本番残存。本番運用で必要な定義は消さない。根拠が薄いものは要確認

### M-3-3: 未使用 JS ファイル（削除確認・必須）

案件の `{フロント}/src/js/` を洗い、**本番で使っていない JS ファイルを削除候補として必ず確認**する。コア常駐・カタログ採用のどちらも対象（正本 `catalog/js/` は案件外のため消さない）。

#### 調査手順

   - `pages/*.js`（および `pages/` 配下のページ専用）
   - その他、エントリから辿れない孤立ファイル（分かる範囲）
2. 各ファイルについて **参照の有無**を調べる:
   - 他 JS からの `import` / 動的 import
   - `setup/initCommon.js`・`setup/project/initProject.js`・`pages/*.js` での初期化呼び出し

3. `pages` エントリは `assets_name` / ルーティング / `pages.php` と突合し、画面が無い・読まれないエントリも候補化
4. `{フロント}/src/js/` 配下で、**再帰的に見て `.gitkeep` 以外のファイルが無いディレクトリ**を探す。該当は **ディレクトリごと** 削除候補にする（`.gitkeep` は単体で出さない）。入れ子で外側も同様なら、外側を 1 件にまとめる。`.gitkeep` 以外のファイルがあるディレクトリは対象外
5. 表で提示する（パス・未使用と判断した根拠・推奨: 削除 / 残す理由があれば注記）

#### 削除しない・慎重にする例

- `lifecycle/`・`setup/` の基盤（`createPage`・`initCommon` 本体など）
- `constans/`・明らかにビルド・全画面基盤が参照する `utils`（`delegate.js` 等。参照があるもの）
- `_template.js`
- 参照解析が曖昧なもの → 削除せず要確認

#### 確認

1. 候補がゼロでも「未使用 JS なし」と明示する（Step を飛ばさない）
2. **`AskQuestion`**: 削除承認 / 一部のみ（チャット） / スキップ
3. 承認分のみ削除。カタログに戻したい汎用部品があれば、削除前に `@js-catalog-adopt`／`catalog/js` への戻しを案内してよい（勝手にカタログへ書かない。承認後）

## HTML 構文（vnu・基本は実施）

### vnu-2: 一括チェックと報告（実施するとき）

作業ディレクトリは、`vnu-pages` がある Makefile のディレクトリ（このリポジトリでは `envs/php` または `envs/wordpress`）。実行すると対象ターゲットがコンテナ起動（`up`）を含む。

| 環境 | 実行するコマンド |
|------|------------------|
| WordPress | `make vnu-pages` のみ。静的 HTML の `make vnu-html` は使わない |
| PHP（公開画面） | `make vnu-pages` |
| PHP（静的 HTML があるとき） | 上に加え `make vnu-html VNU_HTML_DIR=<ディレクトリ>` |

静的 HTML は、PHP 環境で `.html` / `.htm` があるときだけ。実行前にディレクトリ候補をチャットで示し、**`AskQuestion`**（候補のディレクトリ / 別ディレクトリは「その他」 / 静的 HTML は見ない）で決める。断片を外すときは `VNU_HTML_EXCLUDE=<名前>` を付ける。

1. 上のコマンドを実行する。warning も見る（`VNU_ERRORS_ONLY` は付けない）。
2. 結果を要約する（対象数、error、warning、取得失敗。error はパスとメッセージ）。この Step では編集しない。
3. **`AskQuestion`**: 問題なし / 修正に進む / 一部のみ（チャットで指定） / 修正しない
