# manuscript-injection

原稿・コピーをテーマテンプレートへ投入するためのワークフローです。
**主眼は改行の判断と実装**です。原稿の提供形式（Excel・表・チャット貼り付け等）や列・シートの対応は依頼ごとに異なるため、**都度の依頼内容に従う**。

## 実行フロー

1. 依頼で示された原稿ソース・対象箇所・対応ファイルを把握する（未指定なら確認する）
2. 各文言を「見せるコンテンツ」か「読ませるコンテンツ」かに分類する
3. 下記「改行ルール」に従って改行位置を決める（提供原稿の改行をそのままコピーしない）
4. テンプレートへ反映する（固定テキスト直書き / 配列 + `format_template_html()` は `.cursor/rules/project/template/php.mdc` に従う）
5. PC のみ改行が必要な場合はレスポンシブ用 `<br class="hp_hidden_*">` 等で実装する
6. 原稿の内容が WordPress 側の設定（CPT・タクソノミー・カテゴリ・ACF フィールド等）の追加・修正を要する場合は、下記「WordPress設定への反映」に従って設定側も対応する
7. 作業中に見つけた不明点・仕様との相違・原稿の誤りの可能性を控えておき、完了時に一覧で報告する（下記「完了報告」）

ビルド・コンパイル系コマンドは実行しない（`CLAUDE.md`「ビルド・コンパイル」）。

## Excel 原稿の読み取り

原稿が xlsx で提供された場合の読み取り方法。列・シートの対応は依頼内容に従う。

- **read-excel-file**（Node.js）で読む。導入場所・スクリプトの置き場所・読み込み方は `manuscript-sheet` スキル「Excel 出力仕様」内「ライブラリ」を正本とする（`.claude/skills/manuscript-sheet/SKILL.md` を Read する）
- `readExcelFile(path)`（default）で全シートを `[{ sheet, data }]` として取得する。`data` は行×列の値の配列（空セルは `null`）
- **非表示シートも返る**。対象シートは依頼内容とシート名で照合し、全シートを無条件に原稿扱いしない
- セル内改行は `\r\n` で返ることがある。`\n` に正規化してから扱う（改行位置の判断は下記「改行ルール」）
- 取得できるのは **値のみ**。文字色・太字・取り消し線・セル背景などの書式は読めない。色分け等で指示されている原稿の場合は、依頼者に内容を確認する

## 改行ルール

・提供された現行の改行をそのまま設定するのではなく、以下の観点に従って適切な改行を行い対応するようにすること。
・文章は「見せるコンテンツ」と「読ませるコンテンツ」に分類して判断する。改行は意味の区切りで行い、見た目を揃えるためだけの改行はしない。

### 原稿の改行・空行の扱い

・原稿文章内にある改行は**参照程度**とする。そのまま転記せず、改行位置は本ルール（行長の目安・見せる/読ませる・寄せ）に従って都度判断する。
・原稿側に空行（段落区切り）がある場合、投入先のdemo環境の仮テキストが**空行を伴うデザイン**であれば、その空行を反映してよい。
・投入先のデザイン箇所に**空行がない**場合は、原稿側に空行があっても、投入時は空行なしとする。

### 見せるコンテンツ

キャッチコピー・見出し・Feature・CTA・短いカード説明など。

・意味のまとまりで積極的に改行する。
・SPでも改行を維持するのは、改行自体がデザイン・メッセージ性を担うもの（短いキャッチコピー・見出しなど）に限る。それ以外はSP側で解除し、ブラウザの自動折り返しに委ねる。

### 読ませるコンテンツ

サービス詳細・会社紹介・ブログ・ニュース・長文説明など。下記「行長の目安」に加え、テキストの寄せ（左寄せ／中央寄せ）に応じて改行方針を分ける。

#### 行長の目安（50文字前後）

・1行はおおよそ50文字前後を目安とする。
・それを超える場合は、その前後の「、」「。」その他区切りの良い場所で改行する。区切りの良い箇所が無いまま50文字を大きく超えて続けない。
・段落分けに加えて、この目安に沿って行途中の改行を入れる（「強制改行しない」で放置しない）。

#### 左寄せの場合

・上記の文字数の目安に加え、意味のまとまりに応じた改行を許可する。
・カードコンテンツなど、テキスト領域の幅が比較的短い場合は、基本的に改行なしとする。
・SPでは改行を少なくする方針とするが、完全になくす必要はない。大きな文章の塊単位での改行は許容する。
  - 改行を入れる場合、基本は「。」（文末）の位置に限る。「、」や単語区切りでの改行は基本的にしない。
  - すべての「。」で改行するわけではない。原稿側の指示、文章の長さ・塊のまとまりを判断し、改行が必要な箇所にのみ入れる。
  - 改行なしで最後まで詰めて表示するのも許容範囲（改行「必須」ではなく、文章の塊が大きいときに改行を入れることを許容するイメージ）。

#### 中央寄せの場合

・上記の文字数の目安に加え、改行を許可する。
・左寄せよりも短めのスパンで改行する。1文をそのままブラウザの自動折り返しに任せるレベルではなく、句読点や文章の単位で判断し、1行ずつ手動で改行を調整するレベルで行う。
・SPでは幅が変わるため、PCの改行位置をそのまま使い回さず、SP側でも改行位置の調整を必須で行う。

### 全体ルール（PC/TAB/SP共通）

・PC・TAB・SPいずれのサイズでも、1行が1〜3文字になってしまうなど不適切な改行は可能な限り避ける。
・PCとSPで改行の入れ方に差が出る場合は、レスポンシブで切り替えられる実装（`hp_hidden_*` 等の表示切替ヘルパークラス。詳細は下記「実装時の参照」）で対処する。
・PC/SPでテキストの寄せ（中央寄せ⇔左寄せ）が切り替わる要素があるため、都度実装対象を確認し、その時点の寄せに応じた改行方針（上記「左寄せの場合」「中央寄せの場合」）を適用する。

## WordPress設定への反映

原稿の内容が、テンプレートの文言差し替えだけでなく CPT・タクソノミー（カテゴリ等）・ACF フィールドなど WordPress 側の設定変更／追加を伴う場合は、テンプレート反映と合わせて設定側も対応する。

- 対象例: 新規カスタム投稿タイプ・タクソノミーの追加、既存 `category_settings` / `term_settings` への項目追加・変更、ACF フィールドの追加・変更、開発用サンプル投稿（`posts.dev.json` 等）の追加・更新
- 設定ファイルの役割・具体的な記法は次を正本とする。プロジェクト固有のWordPress実装ルールは `.claude/rules/` へ未移行のため、`.cursor/rules/` / `.cursor/skills/` を直接 Read する
  - `post_type_settings` / `category_settings` / `term_settings` 等、`posts.php` の役割と「画面表示は WordPress 実データを使う」境界: `.cursor/rules/project/wordpress/posts.mdc`
  - `posts.php` / `acfFileds.php` / `posts.dev.json` の具体的な記法・手順（ACF フィールド追加時の確認含む）: `.cursor/skills/project-page-info/php-config.md`
- `posts.php` 側の変更は**登録・初期投入の定義**に留め、画面に出す投稿・ターム一覧は WordPress 実データ（`get_terms()` 等）を使う方針は変わらない（`posts.mdc`「画面表示は WordPress 実データ」）
- ACF フィールドを新規追加する場合、`acfFileds.php` をユーザー確認なしに編集しない（`php-config.md`「ACF フィールド設定」）
- `make wp-create-posts` 等、DB へ反映するスクリプトは実行するとデータに影響するため、実行前に依頼者へ確認する

## 完了報告

投入内容の概要に加え、次の **要確認事項** を報告の最後に一覧で示す。該当が無い区分は「なし」と明記する。

| 区分 | 例 |
|------|-----|
| 不明点 | 投入先の箇所が特定できない、原稿の意図が読み取れない、PC/SP どちらの改行か判断がつかない |
| 現状仕様との相違 | 原稿の項目数とデザイン・テンプレートの枠数が合わない、文字量がレイアウトに収まらない、リンク先・画像など原稿に無い要素がある |
| 原稿の誤り・誤字の可能性 | 誤字脱字、表記ゆれ（同じ語の表記違い・全角半角）、数値・日付・固有名詞の不整合 |

- 誤字や表記ゆれと思われる箇所も、**原稿どおりに投入し**、報告で指摘する（依頼者の確認なしに直さない）
- 作業を止めないと進められない不明点は、その時点で `AskUserQuestion` ツールで確認する。それ以外は判断した内容で投入し、一覧に「判断した内容」を添える
- 各項目は、対象ファイル（または画面・セクション）、該当文言、指摘内容の順で書き、対応箇所が分かるようにする

```
## 要確認事項
### 不明点
- about.php / 沿革: 原稿の「2020年」の行を追加先に既存の行が無い → 末尾に追加した
### 現状仕様との相違
- top.php / 強み: 原稿は4項目、デザインは3枠 → 4項目で投入（レイアウト要確認）
### 原稿の誤り・誤字の可能性
- recruit.php / 募集要項:「コミニュケーション」→「コミュニケーション」の誤字の可能性（原稿どおり投入）
```

## 実装時の参照（正本は Cursor 側ルール）

長文のコピーはせず、次を参照する。プロジェクト固有のテンプレート実装ルールは `.claude/rules/` へ未移行のため、`.cursor/rules/` を直接 Read する。

| 内容 | 正本 |
|------|------|
| `<br>` / `\n` / 行配列、**`<br>` 直後のソース改行禁止** | `.cursor/rules/project/template/php.mdc`「改行の表現」 |
| 固定テキスト直書き vs 配列 | `.cursor/rules/project/template/php.mdc`「固定テキストの記述」「リスト的な繰り返しコンテンツ」 |
| `format_template_html()` | `.cursor/rules/project/template/php.mdc`「エスケープと HTML マークアップ」 |
| `hp_hidden_*` 等の表示切替 class | `src/scss/helpers/_helpers.scss` |

PC のみ改行の典型例（プロジェクトの helper に合わせる）:

```html
意味のまとまり<br class="hp_hidden_sp_">続き
```

`<br>` の直後にソース改行・空白を入れない(非表示時にスペースが残るため)。
